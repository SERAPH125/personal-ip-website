我之前把 Codex 的用法拆成五级：指令、任务、作业单、工作流和完整目标。

分级解决的是「AI 能帮你做到哪一步」，但还剩下一个问题：**一个没有编程基础的人，到底应该按什么顺序学？**

我的判断是：Vibe Coding 降低的是敲代码的门槛，没有消除定义问题、判断结果和承担风险的责任。

真正值得学的，不是背下一百条提示词，而是建立一个能反复运转的小闭环：

> 说清目标 → 让 AI 实现 → 看懂变化 → 运行验证 → 出错能撤回。

## 第一阶段 · 先学会不把项目弄丢

零基础最容易犯的错误，不是代码写错，而是不知道 AI 改了什么、文件保存在哪里、出错后如何恢复。

开始使用 Coding Agent 之前，先认识五样东西：

| 基础概念 | 最低学习目标 |
|---|---|
| 文件与目录 | 知道项目在哪，能找到源码和生成文件 |
| 终端 | 能进入项目目录，运行安装、开发和测试命令 |
| Git | 会查看状态、提交版本和撤回错误修改 |
| 浏览器开发者工具 | 能看到页面报错、网络请求和元素样式 |
| 错误信息 | 会复制完整报错，而不是只说「运行不了」 |

不必先系统学习复杂算法和设计模式。先保证项目可以保存、运行和恢复。

> 判断标准：如果 AI 把页面改坏了，你能否回到修改前的版本？如果不能，就还不适合把大型任务完全交给 Agent。

## 第二阶段 · 用一个小项目跑通闭环

第一个项目不要做社交平台、商城或大型 App。更合适的是「个人阅读清单」：

- 可以添加书名或文章标题；
- 可以标记已读和未读；
- 可以按状态筛选；
- 刷新页面后数据仍然存在；
- 手机和电脑都能正常使用。

它足够简单，可以快速看到结果；又包含界面、数据、交互、异常状态和验收，能覆盖一套完整开发闭环。

第一条指令不要写成：

> 帮我做一个好看的阅读网站。

可以改成：

> 创建一个个人阅读清单网页。用户可以添加标题和链接，标记已读状态，按全部、未读、已读筛选。数据保存在浏览器本地。页面需要适配 390px 手机宽度。提交前运行项目现有检查，并说明修改了哪些文件。不要加入登录、数据库和付费功能。

这段任务写清了目标、功能、验收和不做什么。任务越清楚，AI 需要猜的地方越少。

## 第三阶段 · 学会检查，而不是只看页面

页面能打开，不代表任务已经完成。AI 写完后，至少检查七件事：

1. `git diff` 中改了哪些文件；
2. 是否安装了没有必要的新依赖；
3. 项目的检查和测试是否通过；
4. 页面主要流程是否真的能操作；
5. 刷新、空数据和错误输入是否处理；
6. 手机尺寸下是否可用；
7. 是否意外写入密码、密钥或个人信息。

更可靠的提问方式是：

> 请先不要继续修改。列出本次变更、验证命令、尚未验证的风险，以及如何撤回这些修改。

这会把工作流从「继续生成」切换到「解释和验收」。

## 第四阶段 · 从聊天升级为项目规则

做过几个项目后，会发现很多要求每次都在重复：修改前阅读 README、不随意增加依赖、修改后运行测试、同步文档、不碰无关文件、删除与发布前先确认。

这些要求不应该永远留在聊天记录里，而应该写进项目规则。即使更换模型或开启新会话，Agent 仍能知道项目技术、检查命令、风险边界和完成标准。

这也是从「偶尔生成代码」走向「持续维护项目」的分界线。

## 一条适合零基础的四周路线

### 第一周 · 建立安全感

运行一个现有项目，修改一段文字，查看一次 `git diff`，提交一个版本，再撤回一次故意制造的错误。

### 第二周 · 完成一个静态页面

写清目标读者和页面结构，检查电脑与手机布局，学会使用浏览器开发者工具，再发布到测试地址。

### 第三周 · 增加真实交互

添加表单和数据状态，处理空内容与错误输入，增加自动检查。每完成一个小功能就提交一次。

### 第四周 · 建立工作流

编写项目规则，固定验收清单，要求 Agent 先计划再修改，完成一次构建、发布和回滚演练。

四周之后，不一定能成为传统意义上的程序员，但应该具备一个关键能力：知道如何让 AI 工作，也知道如何判断它有没有把事情做对。

## 真正需要掌握的能力

Vibe Coding 的路线可以压缩成五句话：

1. 先学会保存和撤回；
2. 再学会把目标写清楚；
3. 每次只交付一个可验收的小结果；
4. AI 生成之后必须运行验证；
5. 能重复的要求都沉淀成项目规则。

工具会持续更换，模型也会升级。需求、版本、测试、权限和验收不会过时。

如果只能从今天开始做一件事，就创建一个小项目，在第一次修改前提交一个 Git 版本。这不是最炫的技巧，但可能是最重要的安全锁。
