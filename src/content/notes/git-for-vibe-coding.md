Vibe Coding 最容易制造一种错觉：代码是 AI 写的，所以版本管理也可以交给 AI。

真正出问题时，你会发现自己最需要回答的不是「这段代码什么意思」，而是：

- 它到底改了哪些文件？
- 哪一次修改还是正常的？
- 能不能只撤回错误部分？
- 我的原始内容还在不在？

Git 就是这套安全记录。

## 先理解三个状态

Git 官方教程把文件状态分为已修改、已暂存和已提交。对零基础来说，可以把它理解成：

| 状态 | 类比 |
|---|---|
| 已修改 | 草稿纸上已经改了，但还没装进档案袋 |
| 已暂存 | 选好了这次准备保存的修改 |
| 已提交 | 给这批修改拍了一张带说明的快照 |

提交不是上传互联网，也不是发布网站。它只是为当前项目留下一个可以回看的版本。

## 开始任务前先做一张快照

让 Agent 修改项目前，先检查当前状态：

```bash
git status
```

确认现有修改属于谁。不要把自己还没完成的内容误当成垃圾清理掉。

先检查项目是否已有 `.gitignore`，并确认 `.env`、私钥、客户资料、数据库导出和本机配置没有进入待提交列表。不要把 `git status` 当成内容审查，它只显示状态，不会替你判断文件里是否含有秘密。

优先暂存明确的文件：

```bash
git add src/需要保存的文件
git diff --cached
git commit -m "保存修改前基线"
```

文件较多时，可以使用 `git add -p` 逐块选择。只有确认 `.gitignore` 正确、待提交文件都属于当前任务，并用 `git diff --cached` 看过将要提交的内容后，才考虑使用 `git add .`。

> **禁止提交**：`.env`、API 密钥、SSH 私钥、访问令牌、客户数据、未脱敏日志和包含个人绝对路径的配置。发现敏感信息已经暂存时，先取消暂存并撤销密钥，不要只删掉文件后继续提交。

这样即使后面的尝试完全失败，也有清楚的返回点，而且不会为了“做备份”把秘密一起写进 Git 历史。

## `git diff` 比「看起来没问题」可靠

页面只能告诉你最终显示了什么，`git diff` 会告诉你代码实际改变了什么。

重点看四类变化：

1. 是否出现任务范围外的文件；
2. 是否删除了原有内容或配置；
3. 是否写入密钥、账号或本机绝对路径；
4. 是否增加了没有说明的新依赖。

不需要一次看懂所有代码。先确认变化是否符合任务边界，就已经能过滤大量风险。

## 撤回之前先分清对象

「撤回」可能指完全不同的事情：

- 取消暂存，但保留文件内容；
- 丢弃某个文件尚未提交的修改；
- 新建一个提交，反向撤销过去的提交；
- 修改本地最后一次提交说明。

这些操作的风险不同。尤其不要在不清楚目标时，让 AI 直接运行强制重置或覆盖历史的命令。

可以先问：

> 请不要执行撤回操作。先说明准备影响哪些文件、会不会删除未提交内容，以及是否存在可恢复方案。

解释清楚，再执行。

## 一次十分钟的安全练习

创建一个临时项目，完成下面的练习：

1. 新建一个只有标题的网页并提交；
2. 修改标题颜色，查看 `git diff`；
3. 再提交一次；
4. 故意删除标题；
5. 查看状态并恢复尚未提交的删除；
6. 查看两次提交之间的区别。

练习目标不是背命令，而是亲眼看到：文件修改、差异和提交记录之间是什么关系。

## 让 Agent 交付版本证据

任务完成后，可以固定要求它报告：

- 修改文件列表；
- `git diff --stat` 摘要；
- 实际运行的检查命令；
- 尚未提交的变化；
- 推荐的提交说明；
- 安全撤回方式。

Git 不是程序员才需要的高级工具。只要 AI 能在几秒内改动几十个文件，版本记录就是所有使用者都应该掌握的基本防护。

Vibe Coding 可以让你更快向前，但 Git 决定你能不能安全回头。
