# AI 写完代码之后：普通人也能执行的七步验收

AI 写代码最快的阶段，往往是生成的那几分钟。真正决定项目质量的，是生成之后有没有认真验收。

最危险的交付方式是：页面打开了，截图好看，于是直接发布。

一个功能可能同时存在样式正常、数据错误、手机不可用、密钥泄露和无法回滚。下面这七步不要求你精通代码，但能让「看起来完成」变成「有证据完成」。

## 第一步 · 看变化，不看承诺

先让 Agent 停止修改，列出实际变化：

```bash
git status
git diff --stat
```

检查是否出现任务之外的文件、配置、依赖或大段删除。Agent 说「只改了样式」不算证据，差异记录才算。

## 第二步 · 检查新增依赖

一个按钮动画不应该引入一整套大型框架。每个新依赖都意味着新的升级、许可证和安全风险。

让 Agent 回答：

- 为什么现有能力不能完成；
- 新依赖解决什么问题；
- 是否有更小的替代方案；
- 是否同步更新锁文件和安装说明。

解释不清，就先不要留下。

## 第三步 · 运行项目自己的检查

不要让模型临时发明一条「看起来像测试」的命令。优先读取 README、`package.json`、工作流或项目文档，找到仓库已经认可的检查方式。

常见证据包括：

- 类型和语法检查；
- 自动测试；
- 生产构建；
- 格式与静态分析；
- 链接、资源和内容契约测试。

重点不是命令跑过，而是看到退出码、测试数量和失败数量。

## 第四步 · 走一遍真实用户流程

自动测试不能替代真实操作。按照用户完成任务的顺序验收：从正常入口进入、完成主要动作、刷新或重新打开，再确认结果仍然正确。

同时检查空数据、重复点击、错误输入、网络失败和加载中的状态。

## 第五步 · 检查不同尺寸和输入方式

电脑鼠标能用，不代表手机触摸和键盘导航能用。至少检查：

- 390px 手机宽度；
- 普通桌面宽度；
- 导航能否用键盘操作；
- 图片失败时是否有替代信息；
- 表格和代码块是否撑破页面；
- 动画在减少动态效果设置下是否停用。

## 第六步 · 搜索敏感信息

检查代码、日志和构建产物中是否出现 API Key、Token、密码、本机用户名、真实客户资料、内部接口或不应公开的环境变量。

如果 Agent 需要凭证，应该通过环境变量或密钥管理服务提供，而不是写进源码。

## 第七步 · 证明可以撤回

发布前必须知道回退点在哪里。让 Agent 提供本次修改对应的提交、回退后需要重新运行的命令，以及是否涉及数据库或不可逆外部操作。

如果一个修改无法安全撤回，它就应该得到更严格的审批。

## 一张可以直接复制的验收单

> 1. 列出所有修改和新增依赖；  
> 2. 运行仓库规定的完整检查；  
> 3. 报告测试总数、失败数和构建结果；  
> 4. 验证正常流程、空状态和错误输入；  
> 5. 验证手机、桌面和键盘操作；  
> 6. 检查密钥、个人数据和本机路径；  
> 7. 提供可执行的回退方案。

AI 可以帮你完成这张表，但最终判断不能外包。验收不是在挑模型的错，而是在保护未来的自己。
